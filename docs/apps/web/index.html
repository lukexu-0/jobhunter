Resume tailoring web interface

Next.js interface for creating, monitoring, reviewing, and approving local resume-tailoring runs.

  • Apps workspace
  • Pipeline service

Runtime and API boundary

The @jobhunter/web package starts Next.js on 127.0.0.1:3456. Its configured rewrite sends same-origin browser requests from /api/pipeline/:path* to the local pipeline at http://127.0.0.1:3457/v1/:path*. In particular, the initializer canonicalizes a valid URL locally and posts {"jobUrl":"…"} to same-origin /api/pipeline/runs; the browser does not fetch the entered remote URL. The pipeline, not browser code, performs the bounded server-side remote retrieval.

Sources: apps/web/package.json, apps/web/next.config.ts, apps/web/app/lib/pipeline-client.ts, and apps/pipeline/src/api/job-source.ts. See also Pipeline API and preconditions.

Persistent primary navigation

The application root layout renders a persistent sidebar beside the current route’s workspace. Its primary navigation contains Applications, which links to /, and Providers, which links to /providers.

Above 48rem, the shell is a two-column layout: the sticky, vertically scrollable rail is 15.5rem wide including its right divider, and the route workspace fills the remaining display width rather than sitting in a centered frame. The workspace keeps 2rem block and 2.5rem inline desktop padding. At 48rem and below, the shell becomes a one-row, sticky 3rem top navigation with two equal-width, nonwrapping links; the rail loses its right border, gains a bottom border, and marks the current link along its bottom edge.

The Applications link receives aria-current="page" on the home route (/) and on every route whose pathname begins /runs/, including an opened run such as /runs/{runId}. The Providers link receives aria-current="page" on /providers and on every route whose pathname begins /providers/. In each case, the other primary-navigation link is not marked as the current page.

Sources: apps/web/app/layout.tsx, apps/web/app/components/app-sidebar.tsx, and apps/web/app/globals.css.

Applications dashboard

The home page is the Applications dashboard. Immediately below the Applications heading is an always-visible, single-line Job posting URL initializer with the https://company.com/jobs/role placeholder and an adjacent Initialize button. It replaces the former conditional description-entry controls and empty-state creation call to action. The shared strict request contract accepts only a trimmed absolute HTTP(S) URL without credentials, removes a fragment, and caps both entered and canonical URL at 2,048 characters. The button is disabled until that contract accepts the field; on submission it displays Initializing…, disables both controls, and sends the canonical jobUrl. A successful 201 response opens the new run’s detail page.

Changing the URL clears a prior error. A failed initialization retains the URL, restores the controls, and reports the bounded public server message in a role="alert" region. While that error is present, the input has aria-invalid="true" and aria-describedby="job-url-error"; the label is visually hidden but programmatically associated with the field. The initial empty state says No applications yet. Enter a job posting URL above to initialize one.

The table shows target role, organization, updated date, application status, and revision. Target metadata is read from the public job-analysis artifact when it is available; otherwise the interface honestly labels the row as a tailoring run and shows unavailable organization data. Search matches run ID, application-status label, target title, or organization. The State filter includes every application status, and the Updated button switches newest/oldest sorting. Filtering or sorting returns to page 1; the client displays eight runs per page with accessible Previous, Next, current-page, and numbered controls.

While any run is nonterminal, the dashboard refreshes the list every 3 seconds. It presents loading, empty, filtered-empty, and retryable error states rather than inventing job metadata.

Sources: apps/web/app/page.tsx, apps/web/app/components/run-dashboard.tsx, apps/web/app/lib/pipeline-client.ts, and apps/pipeline/src/contracts/index.ts.

Application lifecycle status

Every new run begins with the user-managed application status Applied. The complete set is Applied, Rejected, Interview, Accepted, and Failed. These values record the application lifecycle; the service accepts each value directly and does not require a transition order.

Application status is independent of pipeline execution status. Changing it does not change the run’s queued, active, review, approved, or failed pipeline status, create a pipeline timeline event, or wake the scheduler. In particular, the application value Failed is distinct from a failed pipeline run. The run-detail metadata presents Application status and Pipeline status as separate fields.

On the dashboard, use the State filter to show one application status or all states. Each row has an application-state selector with the same five values; choosing a value updates that run. The detail page shows the current application status but does not provide that edit control.

Update request and failure behavior

The selector sends PATCH /api/pipeline/runs/{runId} through the same-origin rewrite, with Content-Type: application/json and exactly {"applicationStatus":"<value>"}. The pipeline endpoint is PATCH /v1/runs/{runId}; it accepts only one of the five contract values in that strict request shape, then returns the updated run. An invalid request receives 400 with INVALID_REQUEST.

The dashboard waits for that request to succeed before replacing its stored run. While it is pending, only that row’s selector is disabled. If the request fails, the prior application status remains selected and the dashboard shows the alert Application state could not be updated. Try again. so the user can retry without losing the previous state.

Providers page and OAuth controls

Provider access is available on the dedicated /providers page, opened from the persistent sidebar’s Providers link; it is not an expandable part of the Applications dashboard. That route renders the Provider access workspace for two independent local OAuth connections: OpenAI Codex provides access for tailoring and fallback job-posting extraction, and Google Antigravity provides access for visual document inspection.

The page reads connection status, starts a provider-specific onboarding session, opens an HTTP(S) sign-in URL in a new tab with noopener,noreferrer, shows instructions and manual prompts when supplied, polls a pending session every 2.5 seconds, supports cancellation, and permits logout.

Displayed errors and identity/status text are bounded and redact credential-like tokens. The interface does not ask for, display, or submit provider API keys. OAuth connection status is independent for both providers. A disconnected OpenAI Codex account does not disable Initialize: it is required only after a static HTML page has no unique usable structured description and reaches the Luna fallback; deterministic JSON-LD and plain-text imports do not need OpenAI Codex.

Opened-run review workspace

Opening a table row navigates to /runs/{runId}. The detail page refreshes active work every 2.5 seconds and renders a three-pane workspace:

  1. Left pane: run summary, the ordered workflow band, a timestamped run timeline, and job analysis.
  2. Center pane: the current review PDF, page-image visual overlays when QA supplied bounding boxes, zoom controls from 75% to 150% in 25% increments, Fit page, and PDF download/fallback.
  3. Right pane: review actions; visual and deterministic QA; source-cited changes; evidence ledger; edit dispositions; repair report; and the public-artifact download list.

The workflow band represents Analysis, Tailoring, Editing, Compile, Repair, Deterministic QA, Visual QA, and Review. The timeline is sorted by event timestamp and sequence. The page only fetches JSON artifacts marked public and only displays review artifacts for a review or approved run; it shows explicit unavailable/loading/error states for absent or unreadable artifacts.

Sources: apps/web/app/runs/[id]/page.tsx, apps/web/app/components/run-detail.tsx, and apps/web/app/lib/run-detail-artifacts.ts.

Edit, regenerate, approve, and download

Send back for edits
For a reviewable current PDF, enter 1–8,000 characters of comments and send them to the edit agent. Comments request evidence-grounded content changes; they do not directly modify the PDF. The pipeline creates and processes a new revision.
Regenerate for layout
For a reviewable current PDF, request a new machine-regeneration revision.
Approve current revision
For a reviewable current PDF, approve the revision. If visual QA did not pass, the acknowledgement checkbox must be selected before approval is enabled. An approved revision is shown as locked while its public artifacts remain available.
Retry failed run
A failed run has a retry control that queues another attempt from the current public run state.
Download
The current PDF has download controls in the header and viewer. The public-artifact panel lists each eligible downloadable artifact with revision, attempt, and byte count.

Each edit, regeneration, and approval request carries the current PDF’s SHA-256 as its expected hash. The UI disables competing actions while an action or refresh is in progress. If the server rejects an action—such as a stale hash or changed run state—the page displays the bounded public error, reloads the current run, and requires the user to act on fresh state. See pipeline mutation preconditions for the server error codes.

Accessibility and responsive layout

The URL initializer has a programmatic Job posting URL label, shared client/server URL validation, an explicit pending state, and an error alert relationship: its error state sets aria-invalid and names the role="alert" with aria-describedby. The dashboard also exposes table headers, search and state labels, current-page semantics, and accessible pagination. The UI uses live regions for loading, action feedback, zoom output, and alerts; controls have labels where icon-only. The review page preserves a PDF-download fallback when the browser cannot embed a PDF.

The initializer is a two-column grid (minmax(0, 1fr) auto): its full-width, minimum-width-zero URL field and nonwrapping action remain side by side at every viewport, including 320px. Its alert spans the full grid row. This horizontal control does not set a document-level minimum width or create document overflow. Keyboard focus receives a visible outline. The document follows the viewport without a fixed 320px floor while normal outer gutters remain. The navigation mode changes at the viewport-owned 48rem threshold, while dashboard and detail component breakpoints use the available route-workspace container width: the review workflow reorganizes at or below 78rem, and dashboard/detail controls stack or compact at or below 48rem, 35rem, and 20rem as applicable. The applications table, workflow stages, document canvas, and, at ultra-narrow widths, viewer controls retain any necessary horizontal scrolling locally rather than widening the document. The stylesheet honors prefers-reduced-motion: reduce.

The interface uses its original dark canvas and surface palette with bright accessible focus and accent colors; application lifecycle state remains conveyed by both visible labels and distinct control colors. Source: apps/web/app/globals.css.

Troubleshooting and verification

Start both services from the workspace with:

cd apps && bun run dev

If the dashboard cannot load runs, confirm that the coordinated launcher reached http://127.0.0.1:3457/v1/health before starting Next, then refresh the dashboard’s retry action. For context or system-tool problems, run the pipeline package scripts:

cd apps && bun run --cwd pipeline doctor
cd apps && bun run --cwd pipeline context:sync -- --check
cd apps && bun run --cwd pipeline context:sync

auth_absent and auth_expired in doctor output are warnings, not failures; connect or refresh OAuth before the relevant agent or visual QA needs it. A stale/invalid context index or missing required system tool is an error. For installation, focused package checks, and the complete doctor classification explanation, see workspace troubleshooting and pipeline troubleshooting.

Sources: apps/scripts/dev.ts, apps/pipeline/src/system/doctor.ts, and apps/pipeline/scripts/context-sync.ts.
