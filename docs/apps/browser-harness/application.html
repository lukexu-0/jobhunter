Browser harness application operations

The Browser Use harness is a local, human-reviewed application service. It opens one visible Chrome session, prepares an application from supplied candidate evidence, and pauses for human navigation, origin approval, review, and final submission.

  • Pipeline OAuth/model gateway

Ownership boundary: pipeline OAuth, harness browser work

The pipeline process is the sole owner of Provider access and the application-owned OpenAI Codex OAuth connection. Connect OpenAI Codex in the existing web UI’s Provider access controls; the harness does not open the OAuth database, copy credentials, accept a provider API key, select another model, or provide login, refresh, or logout operations.

Instead, the harness creates one reusable local HTTP client for its session and calls the pipeline’s loopback gateway. The fixed model contract is openai-codex/gpt-5.6-sol with high reasoning. The gateway checks that the pipeline’s OpenAI Codex connection is still connected before it resolves a request. If it is not connected, create-session preflight fails before Chrome launches with the fixed actionable error Connect OpenAI Codex in Provider access.

The internal gateway is exactly GET and POST /v1/internal/browser-harness/codex on the pipeline, normally http://127.0.0.1:3457. It is an inference-only route: it neither exposes OAuth material nor offers credential or model-management endpoints. The gateway creates the pipeline’s existing OAuth Codex model, which uses the existing OAuth-only resolver; the Python process has no second authentication-store handle.

Loopback and shared-bearer security

Set one JOBHUNTER_HARNESS_TOKEN value of at least 32 characters in the trusted local environment of both the pipeline and harness processes. The harness uses it for every /v1/ request and when it calls the pipeline gateway. The API compares a digest of the complete bearer value with secrets.compare_digest; the pipeline compares a digest with a constant-time comparison. Missing, malformed, and incorrect credentials are intentionally indistinguishable to each service’s caller.

  • The harness binds Uvicorn only to 127.0.0.1, defaults to port 8765, adds no CORS headers, and has no OpenAPI, Swagger UI, or ReDoc endpoint. Only GET /healthz is unauthenticated and returns {"status":"ok"}.
  • Every harness /v1/ response is Cache-Control: no-store. A missing or wrong harness bearer returns 401 {"code":"unauthorized","message":"Unauthorized"}.
  • The pipeline bridge is dispatched before the pipeline’s public mutation-Origin check so that the loopback harness can use it, but it accepts only its exact path and GET or POST. It is not a browser-facing exception to the public Origin policy and adds no CORS behavior.
  • If JOBHUNTER_HARNESS_TOKEN is unset in the pipeline, the exact gateway path returns 404 NOT_FOUND for either method. A configured token shorter than 32 characters prevents pipeline startup; a short or absent token prevents harness startup. Do not put the value in browser JavaScript, a URL, uploads, source control, or logs.

The pipeline URL is an origin-only loopback HTTP URL (default http://127.0.0.1:3457) without credentials, path, query, or fragment. The harness client disables environment-proxy trust and uses a 300-second request timeout. It sends only the gateway’s fixed request/response protocol; it never falls back to another provider, model, reasoning level, API key, or auth store.

Pipeline gateway protocol

Use the bridge only from the harness or another trusted local backend. GET /v1/internal/browser-harness/codex returns {"modelProvider":"openai-codex","model":"gpt-5.6-sol","reasoning":"high","oauth":"connected"} when Provider access is connected; otherwise it returns 409 OAUTH_REQUIRED. A missing or wrong gateway bearer returns 401 UNAUTHORIZED.

POST requires Content-Type: application/json and a strict object containing a UUID sessionId, UTF-8 systemPrompt of at most 1 MiB, UTF-8 transcript of at most 3 MiB, and optionally an object outputSchema. The schema must be an object with properties, a string-only required array, and additionalProperties: false. The full body, including streamed input, is limited to 4 MiB. The deadline is 300 seconds for both body consumption and model resolution.

Structured requests force the one strict emit_browser_use_output function call; text requests disallow function calls. The bridge fixes storage off, tracing off, low text verbosity, high reasoning, a 16,384-token output maximum, no parallel tool calls, and no retry. It returns only fixed provider/model/reasoning metadata, text or structured output, and nonnegative token usage. It does not return reasoning items, OAuth data, prompts, transcripts, account identity, or provider error bodies.

ConditionGateway response
Wrong media type415 JSON_REQUIRED
Over 4 MiB413 REQUEST_TOO_LARGE
Malformed body, UUID, size, or schema422 INVALID_REQUEST

Install and start locally

The standalone package name is jobhunter-browser-harness; its Python import namespace is jobhunter_browser_harness. It requires Python 3.12 exactly (>=3.12,<3.13). Its runtime pins Browser Use 0.13.4 and pypdf==6.10.2; do not substitute a later pypdf pin when reproducing this environment.

python3.12 -m venv apps/browser-harness/.venv
apps/browser-harness/.venv/bin/python -m pip install -e 'apps/browser-harness[dev]'
apps/browser-harness/.venv/bin/browser-use install

The Browser Use 0.13.4 installer invokes uvx playwright install chromium --no-shell; on Linux it also passes --with-deps. Therefore uvx must be available. The installer command itself does not arrange unattended privilege escalation: satisfy any operating-system dependency/elevation prompt according to the host’s normal administration policy. See the official Browser Use quickstart for Browser Use’s general installation guidance.

The harness’s native launch mode uses an installed system Chrome or Chromium, not the operating system’s everyday profile. Browser Use’s managed Chromium installation can be useful for Browser Use tooling, but it does not replace the harness requirement for a detectable system executable, an explicit --chrome-executable, or a separately running loopback CDP Chrome.

  1. Export one local secret for all trusted backend processes.
  2. Start the pipeline, then connect OpenAI Codex through the existing web UI if it is not already connected.
  3. Start the harness with either native dedicated-profile Chrome or a pre-started dedicated-profile CDP Chrome.
export JOBHUNTER_HARNESS_TOKEN='replace-with-one-local-secret-of-at-least-32-characters'

# Terminal 1: pipeline
JOBHUNTER_HARNESS_TOKEN="$JOBHUNTER_HARNESS_TOKEN" bun run --cwd apps/pipeline dev

# Optional terminal: existing Provider access UI, normally http://127.0.0.1:3456
JOBHUNTER_HARNESS_TOKEN="$JOBHUNTER_HARNESS_TOKEN" bun run --cwd apps/web dev

# Terminal 2: native Chrome; defaults are port 8765 and pipeline port 3457
JOBHUNTER_HARNESS_TOKEN="$JOBHUNTER_HARNESS_TOKEN" apps/browser-harness/.venv/bin/jobhunter-browser-harness \
  --chrome-user-data-dir ~/.jobhunter/browser-harness/chrome

# Or terminal 2: attach only to an already-running loopback CDP Chrome
JOBHUNTER_HARNESS_TOKEN="$JOBHUNTER_HARNESS_TOKEN" apps/browser-harness/.venv/bin/jobhunter-browser-harness \
  --cdp-url http://127.0.0.1:9222

Before creating a session, a trusted operator can verify the bridge metadata without exposing the secret in the command line:

curl -H "Authorization: Bearer $JOBHUNTER_HARNESS_TOKEN" \
  http://127.0.0.1:3457/v1/internal/browser-harness/codex

CLI options are --port (default 8765), --pipeline-url (default http://127.0.0.1:3457), --session-timeout (default 3600 seconds), --chrome-executable, --chrome-user-data-dir, and --cdp-url. CDP and a Chrome executable are mutually exclusive; the CLI also rejects a supplied CDP URL together with --chrome-user-data-dir.

Visible Chrome, dedicated profiles, CDP, and WSL

Native mode auto-detects Chrome/Chromium when --chrome-executable is omitted. It creates and requires a mode-0700, dedicated, non-symbolic-link user-data directory; the default is ~/.jobhunter/browser-harness/chrome. The directory must be outside the operating-system default Chrome/Chromium profile roots. This is intentional: the harness uses persistent login state in a separate profile and does not attach automation to an everyday profile.

For Browser Use 0.13.4, the native path constructs a _PersistentChromeProfile with that user_data_dir and profile_directory="Default". Its profile-copy hook is intentionally a no-op, and the constructed Browser retains that profile rather than reconstructing it as Browser Use’s base profile. The dedicated directory is therefore used in place—not copied to an unmanaged temporary profile—and its harness-site login state persists across sessions.

Chrome is headed (headless=False) and kept alive while the session is open. Native launch sets is_local=True, disables default extensions, retains Chromium sandboxing and normal security, and disables HAR, video, and trace recording. Downloads are private session directories. The browser receives allowed domains as canonical origin/ strings rather than broad host patterns.

Sources: apps/browser-harness/src/browser_harness/browser.py and apps/browser-harness/src/browser_harness/models.py.

Versioned session API and SSE lifecycle

All session routes are under /v1 and require the harness bearer. The service allows one active session, including a session waiting for review or ready for human submission. A concurrent create receives 409 session_active and the active session ID. Validation failures are sanitized 422 invalid_request; commands that do not match the pending gate, state, or limits receive 409 command_conflict.

RouteBehavior
POST /v1/sessionsAccepts multipart input, preflights pipeline OAuth/model readiness before Chrome starts, and returns 202 {"session_id":"UUID","state":"starting","events_url":"…","commands_url":"…"}.
GET /v1/sessions/{session_id}Returns the sanitized snapshot: state, timestamps, public URL, company/role, fixed model metadata, fields, attached file basenames, warnings, revision count, approved origins, and either a catalog error or null.
GET /v1/sessions/{session_id}/eventsStreams authenticated text/event-stream frames with id, event, and JSON HarnessEvent data.
POST /v1/sessions/{session_id}/commandsAccepts one strict discriminated JSON command and returns 202 after the applicable human gate accepts it.
DELETE /v1/sessions/{session_id}Closes a known session and returns 204; repeating it for an already closed known tombstone is idempotent. Unknown or evicted IDs return 404 session_not_found.

The snapshot states are exactly starting, running, awaiting_human_navigation, awaiting_origin_approval, awaiting_human_review, ready_for_human_submit, cancelled, failed, and closed. A failed snapshot has one fixed error code/message: oauth_required, pipeline_unavailable, model_timeout, invalid_model_output, model_failed, browser_failed, application_mismatch, step_limit, or session_timeout. Cancelled and closed snapshots have error: null.

Multipart create contract

POST /v1/sessions requires scalar job_url, personal_information, and resume; it accepts zero to 20 repeated allow_domain values, zero to 10 context uploads, zero to 20 anecdote uploads, and max_steps from 1 through 500 (default 100). The job URL is absolute HTTP(S), has no credentials or fragment, retains its path/query privately, and must use HTTPS unless it is loopback. The harness automatically approves the job origin. Each supplied origin must be canonical with no credentials, query, fragment, wildcard, or duplicate and no path beyond an optional /; HTTPS is required except for loopback fixtures. There can be at most 20 approved origins in total, including the derived job origin and later approved origins.

curl -X POST http://127.0.0.1:8765/v1/sessions \
  -H "Authorization: Bearer $JOBHUNTER_HARNESS_TOKEN" \
  -F 'job_url=https://jobs.example.test/roles/123?source=local' \
  -F 'max_steps=100' \
  -F 'personal_information=@candidate.md;type=text/markdown' \
  -F 'resume=@resume.pdf;type=application/pdf' \
  -F 'context=@background.md;type=text/markdown' \
  -F 'anecdote=@incident.md;type=text/markdown'

Events, resumption, and commands

Events have monotonically increasing IDs. Event names are session_started, agent_step, human_navigation_required, origin_approval_required, review_required, revision_applied, ready_for_human_submit, cancelled, failed, and closed. The agent_step detail contains only step_number and a sanitized current_url; navigation requests contain instruction; origin requests contain origin; revision events contain revision_count; other event details are empty because the event’s snapshot carries public review/terminal state.

Pass a nonnegative Last-Event-ID to replay newer frames. The active session retains 256 events and sends an event: snapshot frame if the requested ID was evicted or is ahead of the current event stream. Idle streams emit a : heartbeat comment every 15 seconds. Disconnecting the SSE client does not cancel the application session. Terminal history holds at most 32 sanitized tombstones.

# Resume/replay the event stream.
curl -N -H "Authorization: Bearer $JOBHUNTER_HARNESS_TOKEN" \
  -H 'Last-Event-ID: 12' \
  http://127.0.0.1:8765/v1/sessions/SESSION_ID/events

# Use only when the corresponding gate is pending.
curl -X POST -H "Authorization: Bearer $JOBHUNTER_HARNESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"type":"approve_origin","origin":"https://ats.example.test"}' \
  http://127.0.0.1:8765/v1/sessions/SESSION_ID/commands
  • {"type":"continue"} is valid only while human navigation is pending.
  • {"type":"approve_origin","origin":"https://…"} is valid only for the exact pending origin and only while the 20-origin cap permits it.
  • {"type":"revise","context":"…"} is valid only during review, must trim to 1–20,000 characters, and is limited to 100 revisions.
  • {"type":"ready"} is valid only during review; {"type":"cancel"} is valid for any nonterminal session.

Uploads, front matter, and evidence precedence

PartRequired form and limit
personal_informationRequired UTF-8 .md, at most 1 MiB.
resumeRequired nonempty .pdf, at most 10 MiB, whose first bytes are %PDF-.
contextZero to 10 UTF-8 .md or .txt files; at most 1 MiB each and 5 MiB combined.
anecdoteZero to 20 UTF-8 .md or .txt files; at most 256 KiB each and 2 MiB combined.

Uploads are streamed to a private per-session directory with mode 0700; generated files use mode 0600. Client filenames are reduced to safe display basenames and never trusted as paths. A bad upload, filename, encoding, extension, byte limit, PDF signature, or front-matter shape removes the partial session input and returns a sanitized 422. This is ordinary recursive deletion, not a claim of secure erasure.

Structured direct information

The optional YAML front-matter mapping in personal_information recognizes only full_name, first_name, last_name, email, phone, street_address, city, region, postal_code, country, linkedin_url, portfolio_url, work_authorization, sponsorship_required, relocation, salary_expectation, and start_date. Every supplied value must be a nonempty string; duplicate keys, merge keys, unknown keys, and nonmapping front matter are invalid. If both first and last name are absent but full_name is present, it is split once at the first whitespace; a one-token full name derives only first_name. The Markdown body is narrative evidence, not a second key/value parser.

The harness extracts résumé text and rejects an unextractable PDF, an individual source exceeding 100,000 characters, or combined résumé/profile/context/anecdote narrative exceeding 250,000 characters. It labels narrative sources with their sanitized basename and category so their provenance remains visible to the model. Explicit front-matter values are excluded from narrative prompt evidence and become domain-scoped Browser Use sensitive placeholders instead.

What may be used, and when

  • Explicit front matter is authoritative for contact, identity, sensitive, and legally significant controls. The harness must not infer legal, demographic, work-authorization, visa/sponsorship, salary, disability, veteran, relocation, background-check, or self-identification answers. If no explicit key exists, the control remains untouched and is reported for review.
  • Ordinary professional controls may use only an unambiguous exact fact from the résumé or attributed profile/context evidence. Only the supplied résumé is uploadable.
  • Anecdotes may be selected and paraphrased only for a relevant professional free-text question and visible job description. They must not invent or transfer metrics, dates, responsibilities, employers, credentials, technologies, or outcomes, and an irrelevant anecdote is not evidence merely because it was uploaded.
  • A human revision is authoritative only for the field it corrects in the current run. Otherwise, missing or contradictory facts remain unfilled and produce a human-review warning.

Browser actions and exact-origin control

The harness keeps Browser Use 0.13.4’s complete default action registry and adds human-gate actions alongside it; it does not remove or replace the default done action. The version-pinned registry is: done, search, navigate, go_back, wait, click, input, upload_file, switch, close, extract, search_page, find_elements, scroll, send_keys, find_text, screenshot, save_as_pdf, dropdown_options, select_dropdown, write_file, replace_file, read_file, and evaluate. Native inputs/selects/uploads, intermediate clicks and keypresses, tabs, scrolling, extraction, and JavaScript evaluation are therefore available for intermediate approved-origin controls.

Approval is exact, not host-suffix or wildcard based: the canonical scheme, host, and effective port must match. Browser Use receives each approved origin as origin/ to avoid its scheme-qualified prefix matcher accepting a lookalike host. Before action dispatch, the harness rechecks the live current origin itself; it rejects non-recovery actions on an unapproved origin. Placeholder replacement is likewise performed immediately before dispatch against the live exact origin, so direct values are available only on an approved origin.

When an Apply route reveals a different origin, the model must request human approval before navigating. After any human navigation, the harness parses the current origin and requests approval if it changed. A successful exact approve_origin command appends only that origin’s origin/ representation to the Browser Use allowlist and adds that origin’s sensitive placeholders. No wildcard is accepted. This protects origin transitions while preserving the full default action set.

Human navigation, review, and final submission

The agent first identifies an active matching posting/form and scans every form step, including knock-out controls. On each step it must complete every accessible, machine-actionable control within approved origins before it asks for human navigation or review; this includes native fields, radios, selects, uploads, intermediate clicks and keypresses, and a site-provided JavaScript interface for a custom widget. A visible control explicitly identified as human-only or manual is different: the agent must not activate it, must finish every other accessible control on that step, and then pauses through request_human_navigation. The same gate is used for login, CAPTCHA, 2FA, inaccessible widgets, missing/contradictory facts, or other manual navigation. It requests an origin gate before crossing an unapproved origin. The operator uses continue only after the requested navigation is complete.

After fields and warnings are handled, the agent uses request_human_review. The review snapshot exposes only sanitized field metadata and warnings. A revise command resumes the same session with the revision as long-term memory, increments the revision count, and requires review again. A ready command ends the model workflow immediately at ready_for_human_submit; it performs no later browser action, and the visible form stays open for the person to inspect and personally submit.

Final-submit limitation: the task instruction says not to activate Submit/Send/Apply-now submission controls, press Enter when it submits, call a submission API through evaluate, or use done to bypass review. The configured workflow and local fixture test this behavior, and every application result fixes submit_attempted to false. This is an instruction-level policy, not a browser-enforced capability boundary: unrestricted default click, send_keys, evaluate, and done actions remain available by design. It is not proof that every model or site interaction is technically incapable of automated submission. The harness does not observe or record the human’s eventual Submit click.

Privacy, redaction, TTL, cleanup, and tombstones

Before Browser Use imports, the package sets ANONYMIZED_TELEMETRY=false and BROWSER_USE_ACTION_TIMEOUT_S=3600. Browser Use, HTTP client, and Uvicorn access logging are restricted to warning-level/no-access-log operation. The agent disables vision, judge, GIF generation, conversation persistence, HAR, video, and trace recording. Candidate narrative, résumé text, context, anecdotes, visible job material, and generated answers necessarily pass to OpenAI Codex through the loopback pipeline gateway; they are not returned by that gateway or copied into harness public API data.

Public snapshots and events strip URL credentials, query strings, and fragments. They report field labels/type/presence rather than field values and safe file basenames rather than paths. Known direct values are redacted from public text (including URL-decoded representations), and review warnings are generalized. Gateway errors are mapped to fixed messages rather than provider response bodies. These controls do not make a public browser client safe to receive the shared bearer, and they do not imply a secure-erasure guarantee.

The session lifetime is absolute from creation: default 3600 seconds, configurable with --session-timeout. Expiry produces failed with session_timeout, including when the session is otherwise ready for human submission. On cancellation, failure, deletion, expiry, or shutdown, the manager signals the gate, awaits/cancels agent setup and work, kills the harness-owned browser, closes the per-session pipeline HTTP client, and recursively removes session artifacts (uploads, agent files, and downloads). It publishes the terminal event and releases the singleton only after cleanup completes. A ready session deliberately retains its visible browser and artifacts until deletion or TTL.

The manager retains at most 32 sanitized terminal tombstones, each with at most 256 retained events; older IDs are no longer addressable. Deleting a terminal tombstone records a closed event/snapshot and remains idempotent once closed. This bounded history is for observing lifecycle state, not for retaining private application artifacts.

Focused tests and live smoke procedure

Run the focused gateway test and the harness test suite after installation; these commands do not require real OAuth or an employer site:

bun test --cwd apps/pipeline test/browser-harness-codex.test.ts
apps/browser-harness/.venv/bin/python -m pytest apps/browser-harness/tests

The repeatable live smoke uses only the repository’s two-origin loopback fixture. It requires a running pipeline with connected OpenAI Codex Provider access, a running headed harness, and the shared bearer. Its control order is deliberate: before the human gate, the configured workflow selects the Deployment systems radio, completes the intermediate click and its non-submitting Enter checkpoint, and uses the visible evaluation-only instruction to call window.setCustomWidget('evaluation-set'). The fixture labels Human Next as human-only; it reveals review only after its required fields, machine controls, and custom widget are complete. The smoke deliberately makes two manual interactions: click that Human Next control, then inspect the ready form and click its Submit control exactly once. It is not an unattended test and must never target an employer site.

JOBHUNTER_HARNESS_TOKEN="$JOBHUNTER_HARNESS_TOKEN" \
  apps/browser-harness/.venv/bin/python apps/browser-harness/scripts/smoke_local.py \
  --harness-url http://127.0.0.1:8765 \
  --pipeline-url http://127.0.0.1:3457

Completed live verification: the live smoke completed successfully against the running OAuth-connected pipeline and native headed Chromium. Both required human clicks were made. It passed the live gateway’s exact openai-codex/gpt-5.6-sol and high metadata and live model-call check; authenticated API/multipart, singleton, and SSE checks; exact dynamic-origin approval; the same-run revision; direct-profile/radio, relevant-anecdote, intermediate click/Enter/evaluation, and human-navigation checks; and the zero configured-workflow-submit assertion before ready_for_human_submit. After the human clicked Submit, the fixture recorded exactly one submission. Deletion then produced the closed tombstone, completed cleanup, and released the singleton so a new session could start. The script’s captured API/SSE privacy scan also passed: it rejects bearer/OAuth tokens, direct profile values, full prompts, answer bodies, provider error bodies, and reasoning summaries.

The completed smoke is behavioral evidence for this configured model workflow and local fixture, including its zero-submit-before-ready assertion. It does not turn the instruction-level final-submit policy into a capability guarantee: the retained unrestricted browser actions still mean the harness cannot prove every model or site interaction is technically incapable of automated submission.
